# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`pex-renderer` is a Physically Based Renderer (PBR) and scene graph for [PEX](https://github.com/pex-gl), built as an ECS (Entity-Component-System) on top of WebGL via `pex-context`. Entities are plain objects made of components (plain data); systems are functions that read/write components and orchestrate rendering.

## Commands

This package is scaffolded and managed with [Snowdev](https://github.com/dmnsgn/snowdev/). Claude does not need to run these — the source is checked manually/visually — but they're useful for reference:

- `npm run dev` (`snowdev dev`): starts a dev server and installs ESM dependencies into `web_modules/` for the browser-based `examples/`.
- `npm run build` (`snowdev build`): lints/formats with ESLint + Prettier, runs TypeScript (type definitions are generated from JSDoc in `types/`), and updates the README API docs from JSDoc.
- `npm run release` / `npm run release:alpha` (`snowdev release`): bumps version, generates changelog, tags a commit. Uses Conventional Commits + Angular preset.

- `npx tsc --noEmit` — quick typecheck (strict mode, `exactOptionalPropertyTypes`) from globally installed `snowdev`

Rendering correctness is validated through the visual examples under `examples/` (served via `index.html`, `examples/index.js`) and manual inspection. `npm test` covers only what a screenshot cannot show: `test/frame-graph.js` (culling, merging, lifetime recycling, load/store derivation) and `test/render-textures.js` (which version of a name a reader gets, and what a mismatch does) — both against a stubbed pool, imported from `lib/` so they need a build first and `test/validate-pipeline-wgsl.js` (WGSL compiles through Dawn).

## Architecture

The core model (see README "Architecture" section):

- **Components are plain data objects.** Each file in `components/` exports a factory function (e.g. `components.geometry(options)`) that returns `{ ...defaults, ...options }`. No behavior lives on components.
- **Systems are functions.** Each file in `systems/` exports a factory `(options) => ({ type, update(entities, ...), dispose(entities) })`. Systems mutate components/entities in place and cache derived GPU resources (buffers, textures, programs) keyed by `entity.id` on an internal `cache` object (e.g. `systems/geometry.js`'s `cache[entity.id]`, exposed back on the entity as `entity._geometry`).
- **Systems communicate through components**, not directly with each other. Data flows: components → systems compute/cache → renderer systems consume for draw calls.
- **System order is maintained by the caller** — there's no scheduler. `render-engine.js` shows the canonical order: `animation → skin → geometry → morph → transform → layer → skybox → camera`, then per-camera in `render()`: `helper → reflectionProbe → light → renderPipeline`.
- **Entities** (`entity.js`) are just `{ id, ...components }` — created via `createEntity({ transform: components.transform(), geometry: components.geometry(...), ... })` and added to a `world` (`world.js`), which holds `entities`/`systems` arrays and drives `update()`/`dispose()`.

### Key modules at the repo root

- `render-engine.ts` — the default bundle of systems for a typical render loop. Exposes `.update(entities, deltaTime)` (CPU-side scene updates plus the sky/probe bakes, bracketed in its own command buffer) and `async .render(entities, cameraEntities, options)` (declares, compiles and executes one frame graph covering **all** cameras; returns the resolved output textures per camera).
- `frame-graph/` — retained-mode frame graph, three phases (see its own section below).
- `fullscreen-geometry.ts` — the fullscreen triangle/quad vertex buffers, memoized per context. Deliberately outside the frame graph: the graph only owns resources whose lifetime is one frame.
- `world.ts` — minimal entity/system container (`add`, `addSystem`, `update`, `dispose`).
- `types.js` / `types/` — JSDoc-derived TypeScript definitions; `types/` mirrors the `components/`, `systems/`, `loaders/` structure. These are generated by `snowdev build` from JSDoc comments — don't hand-edit generated `.d.ts` files, edit the source JSDoc instead.

### Frame graph (`src/frame-graph/`)

Passes and virtual resources are declared every frame, compiled into a plan,
then executed. Modules: `types.ts` (handles, declarations, compiled plan),
`state.ts` (per-frame graph state, the phase machine and its guard), `setup.ts`
(resource and edge recording helpers), `compile.ts` (cull → merge → lifetimes →
load/store → allocate), `pool.ts` (physical resources), `execute.ts`
(descriptors + scoped submit), `inspect.ts` (plain-data view, `memoryTimeline`),
`index.ts` (the `FrameGraph` class).

`FrameGraph` is a class, not a system-style factory: it has no
`update(entities)` and it owns a lifecycle. `state.phase` moves idle →
declaring → declared → compiled → executing, and `requirePhase` is the single
guard behind every "only valid during X" error. Nothing is private, so a debug
overlay can read `state`/`pool` directly; the phases, not visibility, are what
protect the invariants.

Rules that the design leans on — breaking any of them degrades it back into an
ordered pass list:

- **A handle only resolves inside `execute`.** `resolve()` throws elsewhere.
  This is what makes lifetime-based recycling safe.
- **Handles identify a resource, not a version.** Reads bind to the latest write
  declared before them; internal versioning lives in the read/write/write-after-read
  edges. Never expose versioned handles — it invites stale-handle bugs.
- **Declaration order is the execution order.** Setup is sequential, so every
  dependency points backwards: the graph is acyclic by construction, and there
  is nothing to gain from reordering. Only merging changes the pass list.
- **`uniforms` entries that are handles become read edges** and are resolved
  before `execute`. Fullscreen passes rely on this; mesh passes declare `reads`
  explicitly because their bindings are per-draw.
- A pass may not read and write the same handle (WebGPU forbids sampling its own
  attachment). Sub-resource access — writing mip N while sampling N-1 — is
  expressed by writing the handle at a level and resolving a raw view inside
  `execute`; the write-after-write edge supplies the ordering.
- `exportTexture(handle)` marks a resource read outside the graph. That means
  four things, all load-bearing: it survives culling, its last write is stored
  rather than discarded, it gains `TEXTURE_BINDING` (the only way to read a
  texture outside the graph is to sample it, and there is no pass to derive
  that from), and it is **not recycled until the frame ends** — a
  reader outside the graph has no pass to bound its lifetime, so releasing it
  after its last in-graph use would let a later pass draw over what the caller
  is about to read. Anything handed back must be exported: the returned
  output textures, and the shadow maps the light system reads off the components.
- `createTexture({ persistent: true })` goes further: the resource keeps one
  dedicated texture **across** frames, never pooled. Export makes contents
  correct for the rest of the frame; persistent makes the *identity* stable,
  which is what anything holding a texture between frames needs — a debug view
  that must know which frame's data it holds, and pex-gpu's bind group cache,
  which is keyed by texture and would otherwise rebuild every bind group
  sampling it, every frame. Costs one texture that is never reclaimed. Right for
  shadow maps; wrong for post-processing scratch textures. A persistent resource
  is looked up by its descriptor `label`, so that label must be stable and
  unique across frames — it is the resource's identity here, not just a debug
  string as in WebGPU.
- **Never call `createView()` on a resolved texture** — use
  `resolveView(handle, { level, layer })` from the pass context. pex-gpu keys its
  bind group cache by view identity and prunes it through the `GpuTexture`
  wrapper's finalizer, which a bare view is not registered against, so a view
  built per frame leaks a bind group per frame. `resolveView` caches per physical
  texture.
- `render()` is async (`stage()` hooks may be). Drive it from an async
  `gpu.frame` callback: the segment stays open across the tick, so the graph
  joins it rather than opening its own and everything drawn afterwards — GUI
  included — batches into one command buffer. **Declaration must never await
  anything that yields past a browser present**: the open segment acquired the
  swapchain texture when it opened, and presenting destroys it, so the submit
  fails for the entire frame — silently taking the sky and reflection probe
  bakes with it, which run once and clear their dirty flags either way. This is
  why post-processing kicks off its effect `import()`s without awaiting them and
  declares only the modules that have already arrived.
- **Pass names are unique within a frame**, and one graph spans every camera, so
  `render-pipeline.update()` runs once per camera into the same graph. Per-camera
  passes carry the camera id; view-independent work is declared once. Shadow maps
  are the latter — `declareShadowMaps` memoises them on the blackboard, keyed by
  layer, since layer filtering is the only thing that changes the caster set.

What compilation buys is WebGPU-specific: barriers are implicit and there are no
heaps to alias, so the wins are culling, merging adjacent passes that share
attachments (there are no subpasses to fall back on), deriving `loadOp`/`storeOp`
from real lifetimes, deriving usage flags, marking single-pass attachments
`TRANSIENT_ATTACHMENT` (memoryless), and recycling whole textures by lifetime.

Extensibility is four distinct mechanisms, deliberately not one:

- `afterPass(name, hook)` — declare passes right after a named pass enters the
  graph. Every pass is an injection point this way, so positioning against one
  costs nothing on the declaring side: no `stage()` call to add, and no set of
  stage names shadowing the pass list. Synchronous, since `addPass` is.
- `stage(name, payload)` — the boundaries no single pass marks (a phase that
  exists whether or not the pass before it was declared), and the only hook that
  carries a payload and can be awaited. The pipeline runs two: `afterScene`,
  once no more geometry will be drawn, and `beforePostProcessing`, after the
  inverse tone map.
- `blackboard` — values shared between decoupled modules.
- `overridePass(name, transform)` — replace, wrap or drop a pass by name.

`describe(handle)` answers what a resource is — format, size, sample count — so
a module sizes its own textures from what it is about to read.

Reading and writing a texture mid-frame both work, which is the point of having
injection points at all. A pass declared between two writes of the same handle
reads what was there at that point, because the later write picks up a
write-after-read edge. And it can publish a modified image: the pipeline
resolves every scene attachment from the register at the moment it declares that
pass (`colorTarget()`), so republishing `"color"` after the main pass means the
transparent pass, the transmission grab and the transmission front pass all
carry on into the new image, loading rather than clearing it, against the depth
buffer they already share. Modifying in place is the only thing ruled out — a
pass may not read and write one handle — so a mid-scene edit is always a copy
into a new texture.

MSAA is the exception, and it is WebGPU's rather than ours: the scene renders
into the multisampled attachment and resolves into the one everything else
samples, and there is no way to load a single-sample image back into a
multisampled attachment. Mid-scene reads still work (the resolve runs at the end
of each pass that declares it); a mid-scene republish is reported and ignored.
The `afterScene` stage is the answer for anything that has to replace the image
under MSAA: the scene has resolved by then, so from there on every reader and
writer of `"color"` is single-sample and a republish is picked up whatever the
sample count.

### Texture hand-off (`render-pipeline/render-textures.ts`)

Declaration order is execution order, so a module joins the frame at an
injection point rather than wherever it likes. What it needs there is a way to
learn what the frame has produced and to hand back what it produced — that is
`RenderTextures`, one per camera per frame, published on the blackboard as
`renderTextures.<viewId>` and handed to every stage callback. Named for what the
entries are: attachments and sampled results share one register, and "render
target" is D3D/WebGL vocabulary WebGPU doesn't use — `resolveTarget` is the only
"target" in the spec.

It has two operations, and everything uses them: the pipeline's own passes, each
post-processing sub-pass, and injected passes. `set(name, handle)` publishes,
`get(name, requirements?)` reads. `"color"` is the frame's image — whatever was
published under it last is what post-processing, `debugRender` and the blit read
— alongside `"depth"`, `"normal"`, `"emissive"` from the main pass and
`"<effect>.<subPass>"` from post-processing. So splicing passes into a frame is
just publishing `"color"`, and nothing downstream has to be told they exist.

Mismatch has one answer rather than a check per call site: `get` hands back what
a reader can bind, so a multisampled depth texture under MSAA is simply not
returned and the effect sits the frame out. A name keeps every version published
under it, so a pass publishing an unusable `"color"` costs its own contribution
and one logged error naming it rather than a frame that fails validation
somewhere downstream. `require` is `get` plus that report when nothing qualifies.

### Directory structure

- `components/` — one file per component type (e.g. `camera.js`, `material.js`, `geometry.js`, `transform.js`, `skybox.js`, lights, helpers). `components/index.js` re-exports all.
- `systems/` — one file per system, mirroring most components. Subdirectories:
  - `systems/renderer/` — renderer systems (`standard`, `basic`, `line`, `skybox`, `base`) that issue actual draw calls for materials/geometry.
  - `systems/render-pipeline/` — the pipeline that declares passes into the frame graph: culling, shadow mapping, descriptors, and `post-processing.ts` (effect registry with on-demand `import()` per enabled effect). `post-processing/` holds one module per effect (ssao, dof, bloom, combine, smaa, final), each a `PostProcessingEffect` describing its sub-passes; the WGSL they use lives in `shaders/post-processing/`, one file per effect too.
- `loaders/` — asset loading, primarily `glTF.js` for glTF/GLB scene import.
- `utils/` — small standalone helpers (e.g. `blue-noise.js`).
- `utils.js` — shared constants/helpers used across systems: `NAMESPACE` (used for `console.debug`/`console.error` prefixes), temp math scratch objects (`TEMP_VEC3`, `TEMP_MAT4`, etc. — reused to avoid allocations in hot paths), fullscreen quad/triangle geometry, cubemap projection data.
- `examples/` — browser-based visual examples/tests, loaded via `index.html` + `examples/index.js` (reads `?id=` query param to pick an example). This is the primary way to manually validate rendering changes.
- `web_modules/` — ESM dependencies installed by `snowdev dev`/`snowdev install` for browser usage in examples (via `web_modules/import-map.json`). Not hand-edited.

## Conventions specific to this codebase

- Systems that cache GPU resources per-entity must implement `dispose(entities)` to free `ctx` resources (buffers, textures) and clear cache entries — see `systems/geometry.js` for the pattern (dispose specific entities, or clear the whole cache when called with no args).
- Debug logging goes through `if (this.debug) console.debug(NAMESPACE, this.type, ...)`; system-level errors are caught per-entity and logged with `console.error(NAMESPACE, this.type, "update failed", error, entity)` rather than throwing, so one bad entity doesn't break the frame.
- Avoid per-frame allocations in system `update()` loops — reuse the `TEMP_*` scratch objects from `utils.js` instead of creating new vectors/matrices/AABBs.
- Attribute/property names on components sometimes accept multiple aliases (see `attributeMap` in `systems/geometry.js`, e.g. `uvs`/`texCoords`/`uvs0`/`texCoords0` all map to `aTexCoord0`) — check existing alias handling before assuming a single canonical name.

## Coding Style

### Conventions

- Tree-shaking is a hard requirement: free functions, no god object, `sideEffects: false`.
- Public API needs TSDoc comments (snowdev regenerates the README API section — don't hand-edit between the markers or `lib/`).

### Comment style (JS/TS)

- Write comments that explain *why*, not *what* — the code should already say what it does. No journey-style comments, only add notable quirks or not handled edge cases.
- Use JSDoc (/** */) for exported functions, classes, and public APIs; TypeScript signatures already document param/return types, so skip @param/@returns tags
- No comments restating obvious code (e.g. `// increment i` above `i++`)
- Use `// TODO(name): reason` for known follow-ups, never bare TODOs
- Prefer self-documenting names over comments where possible
