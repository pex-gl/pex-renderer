# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`pex-renderer` is a Physically Based Renderer (PBR) and scene graph for [PEX](https://github.com/pex-gl), built as an ECS (Entity-Component-System) on top of WebGL via `pex-context`. Entities are plain objects made of components (plain data); systems are functions that read/write components and orchestrate rendering.

## Commands

This package is scaffolded and managed with [Snowdev](https://github.com/dmnsgn/snowdev/). Claude does not need to run these — the source is checked manually/visually — but they're useful for reference:

- `npm run dev` (`snowdev dev`): starts a dev server and installs ESM dependencies into `web_modules/` for the browser-based `examples/`.
- `npm run build` (`snowdev build`): lints/formats with ESLint + Prettier, runs TypeScript (type definitions are generated from JSDoc in `types/`), and updates the README API docs from JSDoc.
- `npm run release` / `npm run release:alpha` (`snowdev release`): bumps version, generates changelog, tags a commit. Uses Conventional Commits + Angular preset.

- `npx tsc --noEmit` — quick typecheck (strict mode, `exactOptionalPropertyTypes`).

There is no separate test suite in this repo; correctness is validated through the visual examples under `examples/` (served via `index.html`, `examples/index.js`) and manual inspection.

## Architecture

The core model (see README "Architecture" section):

- **Components are plain data objects.** Each file in `components/` exports a factory function (e.g. `components.geometry(options)`) that returns `{ ...defaults, ...options }`. No behavior lives on components.
- **Systems are functions.** Each file in `systems/` exports a factory `(options) => ({ type, update(entities, ...), dispose(entities) })`. Systems mutate components/entities in place and cache derived GPU resources (buffers, textures, programs) keyed by `entity.id` on an internal `cache` object (e.g. `systems/geometry.js`'s `cache[entity.id]`, exposed back on the entity as `entity._geometry`).
- **Systems communicate through components**, not directly with each other. Data flows: components → systems compute/cache → renderer systems consume for draw calls.
- **System order is maintained by the caller** — there's no scheduler. `render-engine.js` shows the canonical order: `animation → skin → geometry → morph → transform → layer → skybox → camera`, then per-camera in `render()`: `helper → reflectionProbe → light → renderPipeline`.
- **Entities** (`entity.js`) are just `{ id, ...components }` — created via `createEntity({ transform: components.transform(), geometry: components.geometry(...), ... })` and added to a `world` (`world.js`), which holds `entities`/`systems` arrays and drives `update()`/`dispose()`.

### Key modules at the repo root

- `render-engine.js` — the default bundle of systems for a typical render loop. Exposes `.update(entities, deltaTime)` (CPU-side scene updates) and `.render(entities, cameraEntities, options)` (GPU draw, per camera, using a render graph).
- `render-graph.js` — collects `renderPass` calls during a frame and submits them to `pex-context` (`ctx.submit`) at `endFrame()`, catching and de-duping per-pass errors.
- `resource-cache.js` / `pipeline-cache.js` / `program-cache.js` — frame-scoped and content-hashed caches for GPU resources (textures, framebuffers, pipelines, shader programs) to avoid redundant allocation/compilation.
- `world.js` — minimal entity/system container (`add`, `addSystem`, `update`, `dispose`).
- `types.js` / `types/` — JSDoc-derived TypeScript definitions; `types/` mirrors the `components/`, `systems/`, `loaders/` structure. These are generated by `snowdev build` from JSDoc comments — don't hand-edit generated `.d.ts` files, edit the source JSDoc instead.

### Directory structure

- `components/` — one file per component type (e.g. `camera.js`, `material.js`, `geometry.js`, `transform.js`, `skybox.js`, lights, helpers). `components/index.js` re-exports all.
- `systems/` — one file per system, mirroring most components. Subdirectories:
  - `systems/renderer/` — renderer systems (`standard`, `basic`, `line`, `skybox`, `base`) that issue actual draw calls for materials/geometry.
  - `systems/render-pipeline/` — the render graph pipeline: culling, shadow mapping, descriptors, and `post-processing/` (bloom, DoF, SMAA, SSAO, combine, final).
- `loaders/` — asset loading, primarily `glTF.js` for glTF/GLB scene import.
- `utils/` — small standalone helpers (e.g. `blue-noise.js`).
- `utils.js` — shared constants/helpers used across systems: `NAMESPACE` (used for `console.debug`/`console.error` prefixes), temp math scratch objects (`TEMP_VEC3`, `TEMP_MAT4`, etc. — reused to avoid allocations in hot paths), fullscreen quad/triangle geometry, cubemap projection data.
- `examples/` — browser-based visual examples/tests, loaded via `index.html` + `examples/index.js` (reads `?id=` query param to pick an example). This is the primary way to manually validate rendering changes.
- `web_modules/` — ESM dependencies installed by `snowdev dev`/`snowdev install` for browser usage in examples (via `web_modules/import-map.json`). Not hand-edited.

## Conventions specific to this codebase

- Systems that cache GPU resources per-entity must implement `dispose(entities)` to free `ctx` resources (buffers, textures) and clear cache entries — see `systems/geometry.js` for the pattern (dispose specific entities, or clear the whole cache when called with no args).
- Debug logging goes through `if (this.debug) console.debug(NAMESPACE, this.type, ...)`; system-level errors are caught per-entity and logged with `console.error(NAMESPACE, this.type, "update failed", error, entity)` rather than throwing, so one bad entity doesn't break the frame.
- Avoid per-frame allocations in system `update()` loops — reuse the `TEMP_*` scratch objects from `utils.js` instead of creating new vectors/matrices/AABBs.
- Attribute/property names on components sometimes accept multiple aliases (see `attributeMap` in `systems/geometry.js`, e.g. `uvs`/`texCoords`/`uvs0`/`texCoords0` all map to `aTexCoord0`) — check existing alias handling before assuming a single canonical name.

## Coding Style

### Conventions

- Tree-shaking is a hard requirement: free functions, no god object, `sideEffects: false`.
- Public API needs TSDoc comments (snowdev regenerates the README API section — don't hand-edit between the markers or `lib/`).

### Comment style (JS/TS)

- Write comments that explain *why*, not *what* — the code should already say what it does. No journey-style comments, only add notable quirks or not handled edge cases.
- Use JSDoc (/** */) for exported functions, classes, and public APIs; TypeScript signatures already document param/return types, so skip @param/@returns tags
- No comments restating obvious code (e.g. `// increment i` above `i++`)
- Use `// TODO(name): reason` for known follow-ups, never bare TODOs
- Prefer self-documenting names over comments where possible
